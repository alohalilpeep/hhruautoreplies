# hh.ru autoreplies

Автоотклики на hh.ru через профиль BitBrowser и Playwright.

Скрипт цепляется к уже запущенному профилю BitBrowser по CDP, поэтому работает
внутри твоего залогиненного окружения: свой отпечаток, свои куки, свой прокси.
Отдельный `playwright install` не нужен — браузер берётся из BitBrowser.

## Установка

```bash
python3 -m venv venv
venv/bin/pip install -r requirements.txt
cp .env.example .env
```

Заполни `.env`: как минимум `PROFILE_ID` и `SEARCH_URL`.

## Запуск

```bash
venv/bin/python hh_autoapply.py
```

По умолчанию `DRY_RUN=True` — скрипт обходит выдачу и логирует, что бы он сделал,
но не откликается. Убедись, что сухой прогон даёт осмысленные статусы, и только
потом ставь `DRY_RUN=False`.

## Как собрать SEARCH_URL

Проще всего настроить поиск на hh руками и скопировать URL из адресной строки.
Полезные параметры:

| Параметр | Пример | Что делает |
|---|---|---|
| `text` | `DevOps OR SRE OR "системный администратор"` | запрос; `OR` обязательно капсом, фразы из двух слов в кавычках |
| `search_field` | `name` | искать только в названии вакансии, а не в описании |
| `experience` | `between3And6` | ещё: `noExperience`, `between1And3`, `moreThan6` |
| `work_format` | `REMOTE` | удалённая работа |
| `area` | `113` | 113 Россия, 1 Москва, 2 Санкт-Петербург |

Без `search_field=name` запрос ловит слова в теле описания, и в выдачу лезут
вакансии, где DevOps просто упомянут в требованиях.

## Статусы

Результат каждой вакансии пишется в SQLite `hh_responses.db`:

| Статус | Значение |
|---|---|
| `applied` | отклик отправлен и подтверждён |
| `already` | на вакансию уже откликались раньше |
| `no_button` | кнопки отклика нет |
| `external` | отклик ведёт на сайт работодателя, пропущено |
| `questions` | вакансия с вопросами или тестовым, оставлено на ручной разбор |
| `needs_letter` | работодатель требует сопроводительное, а `SEND_LETTER=False` — отложено, ничего не отправлено |
| `dry_run` | сухой прогон |
| `error` | исключение на этой вакансии |
| `unknown` | кликнули, но подтверждение не нашли |

Вакансии со статусом `dry_run`, `error` и `needs_letter` не считаются
обработанными и будут перепроверены на следующем запуске, остальные пропускаются.

## Сопроводительное письмо

Текст письма лежит в `letter.txt` рядом со скриптом и не коммитится — там
обычно личные контакты. Шаблон: `letter.example.txt`.

```bash
cp letter.example.txt letter.txt
```

В тексте можно использовать `{title}` и `{company}` — подставятся название
вакансии и компания. Подстановки необязательны: письмо без них уйдёт как есть.
Если `letter.txt` нет, используется встроенная заглушка.

Режим задаётся `LETTER_MODE` в `.env`:

| Режим | Поведение |
|---|---|
| `never` | письмо не прикладывается; вакансии с обязательным письмом получают `needs_letter` и не трогаются |
| `required` | по умолчанию: письмо только там, где работодатель его требует; на остальные отклик одним резюме |
| `always` | письмо везде, включая дописывание после мгновенного отклика |

Важно понимать разницу. На большинстве вакансий hh отправляет отклик сразу
по клику, без попапа — поля письма в этот момент не существует. В режиме
`always` скрипт после отклика жмёт «Приложить сопроводительное письмо» и
дописывает его отдельным шагом. В режиме `required` этот шаг пропускается:
раз hh не показал попап с пометкой «Обязательное поле», значит работодателю
письмо не нужно.

## Лимиты

`DAILY_LIMIT` — свой лимит откликов в сутки, считается по базе. Отдельно скрипт
ловит лимит самого hh и останавливается, если тот исчерпан. После каждого
отклика пауза 20-60 секунд, между остальными переходами 3-8.

## Подъём резюме в поиске

`hh_resume_bump.py` поднимает резюме в выдаче. hh даёт бесплатный подъём раз
в 4 часа; карточка «Поднимите резюме в поиске» появляется на главной только
когда подъём доступен.

```bash
venv/bin/python hh_resume_bump.py          # боевой
venv/bin/python hh_resume_bump.py --dry    # найти карточку, но не кликать
venv/bin/python hh_resume_bump.py --force  # игнорировать свой кулдаун
```

Время последнего подъёма пишется в `bump_state.json`. Пока 4 часа не прошли,
скрипт завершается за доли секунды и браузер не открывает вообще. Если профиль
BitBrowser был открыт до запуска, скрипт оставит его открытым — чтобы не
закрыть браузер под работающим человеком.

### Расписание (launchd)

```bash
cp com.hh.resumebump.plist ~/Library/LaunchAgents/com.hh.resumebump.plist
launchctl load ~/Library/LaunchAgents/com.hh.resumebump.plist
```

Таймер дёргает скрипт раз в 15 минут, а не раз в 4 часа, и это намеренно.
Кулдаун hh отсчитывается от момента подъёма, а таймер — от момента запуска,
поэтому ровно четырёхчасовое расписание приходит на секунды раньше, промахивается
мимо карточки и откладывает подъём ещё на 4 часа. Частый дешёвый опрос
с проверкой кулдауна на своей стороне снимает эту проблему: задержка не больше
15 минут.

Проверить и снять:

```bash
launchctl list | grep resumebump
tail -f bump.log
launchctl unload ~/Library/LaunchAgents/com.hh.resumebump.plist
```

Работает только когда BitBrowser запущен. Если он закрыт, скрипт запишет ошибку
в `bump.log` и выйдет.

## Что лежит локально и не коммитится

`.env` (ID профиля и личные настройки), `hh_responses.db` (история откликов),
`bump.log` и `bump_state.json` (подъёмы резюме), логи launchd, `venv/`.
