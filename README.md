# hh.ru autoreplies

Автоотклики на hh.ru через профиль BitBrowser и Playwright.

Скрипт цепляется к уже запущенному профилю BitBrowser по CDP, поэтому работает
внутри твоего залогиненного окружения: свой отпечаток, свои куки, свой прокси.
Отдельный `playwright install` не нужен — браузер берётся из BitBrowser.

## Состав

| Скрипт | Зачем |
|---|---|
| `hh_autoapply.py` | обход выдачи и отклики, включая анкеты работодателей |
| `hh_answers.py` | банк текстовых ответов на вопросы анкет |
| `hh_choices.py` | вопросы с выбором варианта: радиокнопки и чекбоксы |
| `hh_chats.py` | чаты с работодателями: сбор, разметка, отчёт «куда заглянуть» |
| `hh_stats.py` | статистика откликов и когорты по версиям резюме |
| `hh_questions.py` | разбор накопленного пула вопросов по темам |
| `hh_resume_bump.py` | подъём резюме в поиске раз в 4 часа |

Общая идея всюду одна: **скрипт не решает за человека**. Он собирает данные,
предлагает черновики и отправляет только то, что ты явно одобрил. Всё
неодобренное откладывается, а не отправляется наполовину.

## Установка

```bash
python3 -m venv venv
venv/bin/pip install -r requirements.txt
cp .env.example .env
```

Заполни `.env`: как минимум `PROFILE_ID` и `SEARCH_URL`.

## Запуск

```bash
venv/bin/python hh_autoapply.py
```

По умолчанию `DRY_RUN=True` — скрипт обходит выдачу и логирует, что бы он сделал,
но не откликается. Убедись, что сухой прогон даёт осмысленные статусы, и только
потом ставь `DRY_RUN=False`.

## Как собрать SEARCH_URL

Проще всего настроить поиск на hh руками и скопировать URL из адресной строки.
Полезные параметры:

| Параметр | Пример | Что делает |
|---|---|---|
| `text` | `DevOps OR SRE OR "системный администратор"` | запрос; `OR` обязательно капсом, фразы из двух слов в кавычках |
| `search_field` | `name` | искать только в названии вакансии, а не в описании |
| `experience` | `between3And6` | ещё: `noExperience`, `between1And3`, `moreThan6` |
| `work_format` | `REMOTE` | удалённая работа |
| `area` | `113` | 113 Россия, 1 Москва, 2 Санкт-Петербург |

Без `search_field=name` запрос ловит слова в теле описания, и в выдачу лезут
вакансии, где DevOps просто упомянут в требованиях.

## Статусы

Результат каждой вакансии пишется в SQLite `hh_responses.db`:

| Статус | Значение |
|---|---|
| `applied` | отклик отправлен и подтверждён; в логе `+письмо`, если приложено сопроводительное |
| `already` | на вакансию уже откликались раньше |
| `no_button` | кнопки отклика нет |
| `external` | отклик ведёт на сайт работодателя, пропущено |
| `questions` | вакансия с вопросами или тестовым, оставлено на ручной разбор |
| `answered` | анкета заполнена по шаблонам и отклик отправлен |
| `blacklisted` | компания в `blacklist.txt`, отклик не отправлялся |
| `skipped_question` | среди вопросов есть отброшенный вручную (`skip`) |
| `needs_letter` | работодатель требует сопроводительное, а `LETTER_MODE=never` или текста нет — отложено, ничего не отправлено |
| `resume_hidden` | резюме скрыто от работодателей, отклик не примут |
| `dry_run` | сухой прогон |
| `error` | исключение на этой вакансии |
| `unknown` | кликнули, но подтверждение не нашли |
| `no_reaction` | клик по «Откликнуться» не дал никакой реакции — страница не успела ожить |

Повторяемые статусы — `dry_run`, `error`, `needs_letter`, `resume_hidden`,
`unknown`, `no_reaction`, а при `AUTO_ANSWER=True` ещё и `questions`: такие вакансии вернутся в работу на
следующем запуске, остальные считаются закрытыми.

Список к обработке собирается не только из выдачи, но и **из базы по
сохранённому URL**. Иначе отложенная вакансия к моменту, когда ответ на её
вопросы наконец появился в банке, успевает уйти с первых страниц поиска — и
не возвращается уже никогда.

## Когда прогон останавливается сам

- **Капча.** hh подсовывает её, когда считает поведение автоматическим:
  «Пройдите капчу. Чтобы подтвердить, что вы не робот, введите текст
  с картинки». Отклики в этот момент не проходят, хотя клик доходит до
  страницы. Продолжать нельзя — настойчивость приближает блокировку
  аккаунта. Пройди капчу руками в профиле и запусти снова; если она
  появляется часто, снизь `DAILY_LIMIT`.
- **Серия откликов без подтверждения.** `UNKNOWN_STREAK` подряд идущих
  `unknown` (по умолчанию 8) означают, что систематически ничего не проходит.
- **Свой дневной лимит** и **лимит самого hh**.
- **Браузер закрылся** — мак ушёл в сон или закрыли окно профиля.

Во всех случаях необработанные вакансии не теряются и вернутся на следующем
запуске.

## Сопроводительное письмо

Текст письма лежит в `letter.txt` рядом со скриптом и не коммитится — там
обычно личные контакты. Шаблон: `letter.example.txt`.

```bash
cp letter.example.txt letter.txt
```

В тексте можно использовать `{title}` и `{company}` — подставятся название
вакансии и компания. Подстановки необязательны: письмо без них уйдёт как есть.
Если `letter.txt` нет, используется встроенная заглушка.

Режим задаётся `LETTER_MODE` в `.env`:

| Режим | Поведение |
|---|---|
| `never` | письмо не прикладывается; вакансии с обязательным письмом получают `needs_letter` и не трогаются |
| `required` | по умолчанию: письмо только там, где работодатель его требует; на остальные отклик одним резюме |
| `always` | письмо везде, включая дописывание после мгновенного отклика |

Важно понимать разницу. На большинстве вакансий hh отправляет отклик сразу
по клику, без попапа — поля письма в этот момент не существует. В режиме
`always` скрипт после отклика жмёт «Приложить сопроводительное письмо» и
дописывает его отдельным шагом. В режиме `required` этот шаг пропускается:
раз hh не показал попап с пометкой «Обязательное поле», значит работодателю
письмо не нужно.

## Автоответы на вопросы работодателя

`AUTO_ANSWER=True` включает заполнение анкет по шаблонам из `answers.txt`
(не коммитится, шаблон в `answers.example.txt`):

```
зарплата: От 000 000 ₽
город: Ваш город
опыт: N лет в вашей специальности
```

Темы: `зарплата`, `город`, `опыт`, `формат работы`, `телеграм`.

Отвечает **только если распознаны все вопросы вакансии**. Достаточно одного
неизвестного — вакансия целиком уходит в `questions` и ничего не отправляется.
Половинчатый отклик хуже, чем отложенный.

Отказывается отвечать также когда:

- на вопрос с выбором варианта нет одобренного выбора (см. ниже про
  `hh_choices.py`) — радиокнопку за человека наугад не жмём;
- поле ответа скрыто. В смешанных анкетах поле «уточните» лежит в разметке
  до выбора варианта и раскрывается только после клика; заполнять невидимое
  поле нельзя — `fill()` ждёт видимости 30 секунд и валит прогон;
- вопрос составной — спрашивает больше одной вещи. Признаки: несколько знаков
  вопроса, союз «и», длина больше 140 символов, маркеры второй темы. Примеры
  реальных: «укажите зарплатные ожидания **и** желаемый формат сотрудничества»,
  «уточните локацию (город) **и** рассматриваемый формат работы»;
- число полей на странице не совпало с числом вопросов.

Отклики с заполненной анкетой получают статус `answered` и считаются
в дневном лимите наравне с `applied`.

### Банк ответов

Вопросы работодателей копятся в таблице `answer_bank`. Работа с ней:

```bash
venv/bin/python hh_answers.py --fill        # завести строки под новые вопросы
venv/bin/python hh_answers.py --export      # выгрузить в answers_edit.txt
# правишь answers_edit.txt
venv/bin/python hh_answers.py --import      # вернуть правки в базу
venv/bin/python hh_answers.py --approve-all # одобрить черновики
```

В txt правится текст после `ОТВЕТ:` и строка `СТАТУС:`. Привязка идёт по
строке `ID`, а не по позиции, поэтому блоки можно переставлять и удалять.
Ответ читается до следующего разделителя, то есть может быть многострочным.

Отправляются только ответы со статусом `approved`. Статус `needs_input`
не одобряется оптом: там ответ требует личных данных или опыта, которого
нет в резюме.

### База знаний

Вопросы повторяются по смыслу, но не по формулировке: про зарплату спрашивают
37 разными способами, и раньше один и тот же ответ приходилось одобрять
37 раз. База знаний хранит **один факт на тему** — `knowledge.txt` рядом со
скриптом, не коммитится (там зарплата и контакты).

Формат блока — тема, ключи для распознавания, текст ответа:

```
== мониторинг
ключи: мониторинг|prometheus|grafana|zabbix|обсервабилит|алертинг|метрик
Да, собирал наблюдаемость с нуля. Стек: Prometheus для метрик, Grafana
для дашбордов, Alertmanager для оповещений...
```

`hh_answers.py --new` заводит новые вопросы и **подставляет черновик ответа**
из базы, если тема узнана. Дальше как обычно: проверяешь и одобряешь.

**База знаний ничего не отправляет сама** — это принципиально. Работодателю
уходит только `approved` из банка, привязанный к точному тексту вопроса.
Иначе вопрос «Есть опыт с Deckhouse?» попал бы в тему `kubernetes` и уехал
бы общий ответ про Helm и Argo CD — то есть автоматическое враньё.

Темы из `answers.txt` — другой механизм и живут отдельно: их пять, все
фактические (зарплата, город, опыт, формат, телеграм), и они отвечают
**вживую без одобрения**. Расширять этот список техническими темами нельзя
по той же причине.

Смысловой разбор того, что ключи не поймали, делается в диалоге с Claude:
он читает новые вопросы и раскладывает по темам. Регулярки при этом не
решают, *что значит* вопрос — они только ищут точное совпадение в банке.

### Ответы, которые нужно составить вручную

Блоки со статусом `needs_input` — это вопросы, на которые нельзя ответить
по резюме: личные данные, форма оформления, конкретный опыт с технологией,
которая в резюме не заявлена. Шаблон тут не подходит, а выдумывать опыт
нельзя — это вскроется на первом же собеседовании.

Рабочий порядок такой:

1. Открываешь блок в `answers_edit.txt` и смотришь, чего не хватает —
   в тексте ответа стоит пометка, какой именно информации нет.
2. Обсуждаешь формулировку в чате с Claude: говоришь, что из этого твой
   реальный опыт, Claude собирает текст.
3. Вставляешь готовый текст после `ОТВЕТ:` в том же блоке.
4. Меняешь `СТАТУС: needs_input` на `готов` — только у тех блоков, которые
   проверил.
5. `venv/bin/python hh_answers.py --import`

Одобрять `needs_input` оптом нельзя специально: `--approve-all` их не
трогает, чтобы непроверенный текст не ушёл работодателю.

Если вопрос неинтересен — не отвечай, а удали блок целиком: вакансии
с этим вопросом перестанут обрабатываться (см. ниже).

## Вопросы с выбором варианта

Примерно треть анкет — не свободный текст, а радиокнопки и чекбоксы. Они
живут в том же `answer_bank`, но в отдельных колонках `choice` и
`choice_status`: один и тот же вопрос у одного работодателя бывает
радиокнопкой, а у другого свободным полем, и затирать текстовый ответ
подписью варианта нельзя.

```bash
venv/bin/python hh_choices.py --scan     # обойти отложенные вакансии и снять варианты
venv/bin/python hh_choices.py --draft    # проставить черновики выбора
venv/bin/python hh_choices.py --export   # выгрузить в choices_edit.txt
# правишь choices_edit.txt: строки ВЫБОР и СТАТУС
venv/bin/python hh_choices.py --import
venv/bin/python hh_choices.py --list
```

Форма отклика открывается **прямой ссылкой** `vacancy_response?vacancyId=…`,
без нажатия «Откликнуться»: на части вакансий hh отправляет отклик мгновенно
по клику, и кликать ради сбора данных нельзя.

Черновики выводятся из уже одобренных текстовых ответов: да/нет, грейд, шкалы
самооценки, списки знакомых технологий. Если текстовый ответ стоит в
`needs_input`, выбор тоже уходит к человеку — иначе шкала бодро проставляет
«4 (опыт 3-6 лет)» там, где опыта нет.

При одобрении проверяется четыре вещи:

- подпись должна существовать среди вариантов — посимвольно;
- на радиокнопке ровно один вариант;
- взаимоисключающий вариант («Ни с одним из перечисленных», «Документ
  отсутствует») не совмещается с другими;
- пустой выбор не одобряется никогда, даже со статусом `approved`.

**Разные работодатели подписывают одно и то же по-разному:** «Удаленно»,
«Удаленка», «Полностью удаленный (Все города РФ)». Банк хранит одну подпись
на вопрос, поэтому при смене формулировки вакансия откладывается — это
намеренно. Подставлять по похожести нельзя: разница между «Все города РФ» и
«вне РФ» слишком дорогая. Правится одной строкой в базе.

**«Свой вариант»** (`value=open`) не выбирается никогда: он раскрывает поле
произвольного текста, а его за человека не пишут.

## Чаты с работодателями

Отдельная от анкет история: в анкете свободный ввод, в чате живой диалог.
Скрипт чаты **читает и размечает, но не отвечает** — сообщение живому HR
не откатишь.

```bash
venv/bin/python hh_chats.py --scan --new   # добрать новые чаты и непрочитанное
venv/bin/python hh_chats.py --attention    # куда стоит заглянуть самому
venv/bin/python hh_chats.py --scan         # полный обход, нужен один раз
```

В базу пишутся **все** сообщения (`chat_messages`), а не только вопросы:
отказы и приглашения нужны для статистики не меньше. Каждое размечается —
`отказ`, `вопрос`, `автоответ`, `скрининг`, `приглашение`, `бот`, `инфо`.
Порядок проверок в `classify_message()` и есть вся логика:

- отказ важнее приглашения: «к сожалению, не готовы пригласить»;
- живой вопрос важнее вежливого вступления: HR часто начинает со «Спасибо
  за отклик!», и такое письмо целиком уезжало в автоответы;
- шаблонная отписка важнее интереса: «мы свяжемся с вами» ловится почти
  любой регуляркой про интерес, хотя интереса там нет;
- автоскрининг (ГигаРекрутер, видеоинтервью, тесты) — не приглашение:
  hh считает его собеседованием, живого человека там нет.

Тексты хранятся целиком, поэтому правки классификатора можно катать по базе
без повторного похода в браузер.

`--attention` показывает чаты, где последнее слово осталось за работодателем
и это вопрос или приглашение. Чаты с отказом пропускаются. Свои же
сопроводительные письма отфильтрованы: hh не помечает автора у исходящих,
и они выглядят как входящие.

**Не полагайся на отметку «непрочитано»**: чат, открытый руками в интерфейсе
hh, её теряет. Проверка на реальных данных: среди чатов без непрочитанного
у 14% были входящие сообщения — и в их числе единственное за всю историю
живое приглашение с телефоном. Поэтому `--new` опирается на нашу базу
(«мы этот чат уже читали»), а не на отметку hh.

Список чатов виртуализированный и обходится прокруткой. Потолок прокруток —
предохранитель от вечного цикла, а не способ остановиться: при лимите в 60
итераций обход тихо обрывался ровно на 300 чатах, хотя их было 568.

## Статистика

```bash
venv/bin/python hh_stats.py --snapshot "заметка"   # слепок состояния с hh
venv/bin/python hh_stats.py --daily                # отклики по дням
venv/bin/python hh_stats.py --collect              # подтянуть статусы откликов
venv/bin/python hh_stats.py --cohorts              # разрез по версиям резюме
```

`RESUME_VERSION` в `.env` штампуется на каждый отклик. Поменял резюме —
подними версию, и дальше видно, как меняется конверсия между редакциями.

Что важно понимать про эти цифры:

- **«Собеседование» у hh включает автоматический скрининг.** Сбер шлёт
  приглашение к ГигаРекрутеру всем откликнувшимся, РУСАЛ — ссылку на бота.
  Отличить от живого приглашения по счётчику нельзя.
- **Дата в списке откликов — дата отклика, а не дата отказа.** Поэтому
  «сколько отказов пришло во вторник» ретроспективно не построить, только
  разницей между слепками.
- **Приглашений по тегам обычно ноль,** даже когда в чатах зовут на созвон.
  Реальный интерес ищи через `hh_chats.py --attention`.

### Отказ от вакансий

**Удалить блок из `answers_edit.txt`** — вопрос уходит в статус `skip`,
и вакансии с этим вопросом больше не обрабатываются никогда.

Удалением считается только то, что пропало из списка `# EXPORTED:` в шапке
файла, поэтому выгрузить и править кусок файла безопасно — остальные вопросы
не пострадают.

**Компанию целиком** — в `blacklist.txt`, одна строка на компанию, совпадение
по части названия, регистр не важен:

```bash
venv/bin/python hh_answers.py --block "Название компании"
```

Такие вакансии получают статус `blacklisted`, и по ним не делается ни одного
клика — проверка идёт до кнопки отклика.

## Лимиты

`DAILY_LIMIT` — свой лимит откликов в сутки, считается по базе. Отдельно скрипт
ловит лимит самого hh и останавливается, если тот исчерпан. После каждого
отклика пауза 20-60 секунд, между остальными переходами 3-8.

## Подъём резюме в поиске

`hh_resume_bump.py` поднимает резюме в выдаче. hh даёт бесплатный подъём раз
в 4 часа; карточка «Поднимите резюме в поиске» появляется на главной только
когда подъём доступен.

```bash
venv/bin/python hh_resume_bump.py          # боевой
venv/bin/python hh_resume_bump.py --dry    # найти карточку, но не кликать
venv/bin/python hh_resume_bump.py --force  # игнорировать свой кулдаун
```

Время последнего подъёма пишется в `bump_state.json`. Пока 4 часа не прошли,
скрипт завершается за доли секунды и браузер не открывает вообще. Если профиль
BitBrowser был открыт до запуска, скрипт оставит его открытым — чтобы не
закрыть браузер под работающим человеком.

### Расписание (launchd)

```bash
cp com.hh.resumebump.plist ~/Library/LaunchAgents/com.hh.resumebump.plist
launchctl load ~/Library/LaunchAgents/com.hh.resumebump.plist
```

Таймер дёргает скрипт раз в 15 минут, а не раз в 4 часа, и это намеренно.
Кулдаун hh отсчитывается от момента подъёма, а таймер — от момента запуска,
поэтому ровно четырёхчасовое расписание приходит на секунды раньше, промахивается
мимо карточки и откладывает подъём ещё на 4 часа. Частый дешёвый опрос
с проверкой кулдауна на своей стороне снимает эту проблему: задержка не больше
15 минут.

Проверить и снять:

```bash
launchctl list | grep resumebump
tail -f bump.log
launchctl unload ~/Library/LaunchAgents/com.hh.resumebump.plist
```

Работает только когда BitBrowser запущен. Если он закрыт, скрипт запишет ошибку
в `bump.log` и выйдет.

## Что лежит локально и не коммитится

`.env` (ID профиля и личные настройки), `letter.txt` (сопроводительное),
`answers.txt` и `answers_edit.txt` (ответы на анкеты), `choices_edit.txt`
(выбор вариантов), `chat_answers_edit.txt`, `blacklist.txt`,
`hh_responses.db` (история откликов, пул вопросов, банк ответов, чаты),
`bump.log` и `bump_state.json`, логи launchd, `venv/`.

## Ограничения, о которых стоит знать

- **Скрипт работает внутри профиля BitBrowser.** Если мак уснёт, окно закроют
  или оборвётся сеть, связь по CDP рвётся и прогон останавливается. Вакансии
  при этом не теряются: необработанные вернутся на следующем запуске.
- **Семантическое расширение поиска hh.** Даже с `search_field=name` в выдачу
  попадают Python Developer, Data Engineer и стажёры QA. Стоп-лист есть только
  по компаниям, по названию вакансии — нет.
- **Дубли.** Один работодатель публикует вакансию под несколькими id;
  дедупликация идёт по id, поэтому на такое можно откликнуться дважды.
- **Когортное сопоставление неполное.** `--collect` находит около половины
  откликов: hh показывает названия без грейда, а компании без правовой формы.
  Проценты в разрезе версий резюме считаются по выборке.
